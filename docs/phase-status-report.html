A시뮬레이션 엔진

"무엇이 일어났는가"에 답하는 계층. 확률 기반 화재 확산 모델을 폐기하고 실단위 질량수지 엔진으로 처음부터 다시 만들었습니다.

어제 완료

  • 범용 엔진 재작성 모듈 3개든 15개든 동작. 하드코딩된 ID 없음.
  • NASA 1차 자료 교정 SMAC(JSC 20584 Rev C), Saffire I·II, IMV 유량, ISS 감지기 임계값, NASA-STD-6001B, MIL-STD-1629A 원문 확인.
  • 무차원 지표 → 실단위 전환 종별 농도 mg/m³, 유량 m³/s, 소광계수 1/m. 부수 효과로 연기 다중 홉 전파가 자동 해결.
  • 출처 표기 체계 상수 8개 VERIFIED_, 29개 ASSUMED_. 접두어 없는 상수가 생기면 빌드 실패.
  • 탐지를 계산으로 전환 연기가 실제로 경보 수준에 도달하는 시각을 엔진이 계산. 환기를 끄면 자기 경보가 늦어지는 결합까지 반영.
  • 승무원↔시스템 결합 운용자가 없으면 시스템 사용 불가, 수리 담당자가 현장에 있어야 복구. leave-one-out criticality가 실제 수치를 내기 시작.

남은 작업

  • HIGH몬테카를로 결함 수정 montecarlo.py가 RETURN/HABITATION을 하드코딩. 다른 capability를 쓰는 시나리오에서 카운트가 공허하게 n/n으로 나옴. 현재 Phase C 어댑터가 우회 중.
  • HIGH화학종 수율 확보 연료 mg당 CO/HCN/soot 발생량. 최대 데이터 공백. 지상 시험값은 전용 불가 — Saffire가 미소중력에서 열분해 확산 18~24배 느림을 확인.
  • MID소광계수 1차 자료 확인 7.6 m²/g를 문헌값으로 썼으나 원문 미확인.
  • MID장비 내성·승무원 시간 장비 내열 한계, 대응·이동 시간이 전부 가정값. 훈련 기록이 공개되지 않음.
  • MID대기 조건 피드백 압력·산소 농도를 상태로만 들고 있고 화재 거동에 반영하지 않음. Saffire 근거를 붙이기 좋은 다음 후보.
  • LOW열 모델 정교화 현재는 열수지가 아닌 조잡한 대리값.
  • LOW화재 외 사고 유형 감압·전력 상실 등은 미구현. leak은 연결 타입으로만 존재.

B제품 계층

사람이 우주선을 만들고 사고를 주입하는 계층. IBM Bob으로 별도 제작된 것을 받아 실제 엔진에 연결했습니다.

어제 완료

  • 깨진 가상환경 복구 받은 .venv가 다른 PC의 miniconda 경로를 가리켜 실행 불가 상태. 재생성.
  • PhaseASimulatorAdapter camelCase 스키마 ↔ 엔진 모델, 액션 ID 어휘, 결과 형태를 3중 번역. 프런트엔드 코드는 문구 외 무수정.
  • 목 → 실엔진 전환 엔진을 못 찾을 때만 목으로 폴백. GET /가 활성 어댑터를 보고.
  • Advisor 탭 추가 Phase C 결과 표시. 비교 표는 Phase B 의도대로 권고 없는 상태 유지.
  • 배포본 정리 298 MB → 0.3 MB. 압축 해제 후 실행까지 검증 완료.

남은 작업

  • MID분석 요청 비동기화 현재 동기 방식. 시뮬레이션 2.4초 + LLM 7회 호출을 한 요청이 물고 있어 타임아웃 위험. job-id + 폴링으로 전환 필요.
  • LOW폴더명 일관성 Phase b만 대소문자·형식이 phase-c와 다름. 이름 변경 시 launch 설정도 함께 수정 필요.
  • LOWnpm 취약점 경고 2건 개발 의존성. 로컬 PoC에는 무해하나 공개 전 점검 권장.

C다중 에이전트 의사결정 지원

"그것이 무엇을 의미하는가"에 답하는 계층. 시뮬레이터를 대체하지 않고 해석하며, 최종 판단은 사람이 합니다.

어제 완료

  • 계약 기반 어댑터 계약서가 명시한 간극 9개를 전부 폐쇄. 엔진을 import하는 파일이 하나뿐임을 AST 검사로 강제.
  • 그라운딩 검증기 R1~R8 기계 검사. 에이전트가 말한 모든 숫자를 시뮬레이션 출력과 대조하고, 위반은 고치지 않고 운영자에게 노출.
  • 의미 이벤트 추출 120 프레임 → 10~30개 이벤트. capability 전환은 프레임에 없어 파생 계산하고 derived로 표시.
  • 에이전트 7종 Hazard · Crew Safety · Systems · Mission · Evidence · Critic · Coordinator.
  • NASA 근거 코퍼스 검증된 6개 출처 9개 청크. 위치 표기 없는 인용은 적재 단계에서 거부.
  • Phase B 통합 POST /api/analyze, GET /api/advisor/status, Advisor 탭.

남은 작업

  • BLOCKED실제 Granite 검증 WATSONX 키 필요. 프롬프트가 실모델을 만난 적 없음. 스키마 준수 재시도 1회가 부족할 수 있고, 근거 포인터 표기를 모델이 지킬지 미지수.
  • HIGH에이전트 5종 명세 확정 Systems·Mission·Evidence·Critic·Coordinator는 원본 스펙이 11절 중간에서 잘려 제가 제안한 것. 코드에 PROPOSED로 표시됨. 원본이 나오면 role과 project()만 교체.
  • MID다중 액션 심층 분석 전문 에이전트는 현재 기준 액션 1개만 깊게 봄. 전 액션 분석은 LLM 비용이 배수로 증가.
  • MIDcriticality 액션별 산출 현재 기준 액션 하나에 대해서만 leave-one-out 실행.
  • LOW파생 이벤트 정밀화 SMAC 초과 시각을 요약이 주지 않아 연기 도달 시점에 앵커링. 표시는 해두었으나 개선 여지.

→권장 진행 순서

의존 관계를 고려한 순서입니다. 1번이 나머지 여러 항목의 판단 근거가 되므로 가장 먼저 처리하는 것이 좋습니다.

순서할 일페이즈왜 이 순서인가
1 WATSONX 키 설정 후 doctor --live C Advisor가 실제로 동작하는지 확인하는 유일한 방법. 이후 모든 프롬프트 작업의 전제.
2 CLI로 첫 분석 실행, 위반 목록 확인 C 브라우저보다 출력이 다 보여 프롬프트 문제를 찾기 쉬움. 위반이 많으면 프롬프트 조정.
3 에이전트 5종 명세 확정 C 원본 요구사항이 있으면 지금 교체하는 편이 나중보다 저렴.
4 몬테카를로 capability 하드코딩 수정 A 데모 시나리오에서는 드러나지 않지만, 팀원이 새 시나리오를 만들면 바로 문제가 됨.
5 분석 요청 비동기화 B 1~2번에서 실제 응답 시간을 측정한 뒤에 결정하는 것이 합리적.
6 화학종 수율 등 데이터 공백 조사 A 시연에는 영향이 없고, 모델 신뢰도를 높이는 장기 과제.
시연 관점에서

1~2번만 끝내면 전 구간 시연이 가능합니다. 우주선 구축 → 사고 주입 → 실단위 시뮬레이션 → 조치 비교 → 다중 에이전트 분석 → 권고까지 이어지고, 나머지 항목은 모두 품질·견고성 개선이지 기능 공백이 아닙니다.

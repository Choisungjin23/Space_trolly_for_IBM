우주선에 불이 났을 때,
무엇을 해야 할까

우리가 만든 시스템이 무슨 일을 하는지 코딩을 몰라도 이해할 수 있게 풀어 쓴 문서입니다. 전문 용어는 처음 나올 때 점선으로 표시했고, 맨 아래 사전에서 뜻을 볼 수 있습니다.

2026-08-23 읽는 데 약 12분 사전 항목 18개

한 문장으로

우주선에서 불이 났을 때, 어떤 조치를 취하면 어떤 결과가 벌어지는지 미리 계산해 보고, AI 전문가들이 그 결과를 해석해 사람에게 보고하는 시스템입니다. 최종 결정은 언제나 사람이 합니다.

비유하자면

조종사가 실제로 비행기를 추락시켜 보지 않고도 비행 시뮬레이터에서 위기 상황을 연습하는 것과 같습니다. 다만 우리 시스템은 한 걸음 더 나아가서, 시뮬레이션 결과를 놓고 화재 전문가·안전 담당·시스템 담당·임무 담당이 회의를 열어 각자의 관점에서 의견을 내고, 그 의견을 종합해 지휘관에게 보고서를 올립니다.

왜 필요한가

우주선에서 불이 나면 승무원은 몇 분 안에 결정을 내려야 합니다. 그런데 선택지마다 득과 실이 다릅니다. 불이 난 방을 완전히 밀봉하면 불은 잡히지만 그 방의 장비를 영영 못 씁니다. 환기를 끄면 연기 확산은 막지만 희석도 함께 잃습니다. 문 하나만 닫으면 연기가 다른 길로 돌아갑니다.

사람이 몇 분 안에 이 모든 경우의 수를 머릿속으로 계산할 수는 없습니다. 그래서 컴퓨터가 계산하고, AI가 해석하고, 사람이 결정하도록 역할을 나눴습니다.

세 조각이 어떻게 이어지나

시스템은 세 부분으로 나뉘어 있고, 각각을 Phase A · B · C라고 부릅니다. 순서대로 쌓아 올린 구조라서 A가 없으면 B가, B가 없으면 C가 의미가 없습니다.

A 계산기 — 불이 어떻게 번지고 누가 위험해지는지 계산 완료
B 화면 — 사람이 우주선을 그리고 버튼을 누르는 곳 완료
C 전문가 회의 — AI들이 결과를 해석하고 권고안을 작성 완료 · 검증 대기
이 시스템의 핵심 원칙

숫자는 계산기가 만들고, AI는 절대 숫자를 지어내지 않습니다. AI가 "연기가 4개 방에 도달했다"고 말하면, 그 4라는 숫자는 반드시 계산 결과 안에 실제로 있어야 합니다. 없으면 시스템이 자동으로 잡아내서 사람에게 "이 AI가 근거 없는 말을 했다"고 표시합니다.

A계산기

우주선을 방과 통로로 이루어진 지도로 표현하고, 불이 났을 때 연기가 어느 통로로 얼마나 흘러가는지를 30초 단위로 1시간 동안 계산합니다. 이걸 시뮬레이션이라고 부릅니다.

어제 한 일

  • 계산 방식을 완전히 바꿨습니다. 원래는 "35% 확률로 옆방에 불이 붙는다" 같은 방식이었는데, 그 35%라는 숫자에 아무런 근거가 없었습니다. 그래서 실제 공기 흐름을 계산하는 방식으로 바꿨습니다. "환기 팬이 초당 0.07세제곱미터를 밀어내고, 방 크기가 105세제곱미터니까 농도가 이만큼 오른다" 같은 식입니다.
  • NASA 실제 문서에서 숫자를 가져왔습니다. 원문 PDF를 직접 열어 표를 읽었습니다. 예를 들어 일산화탄소의 1시간 노출 허용 농도는 425ppm입니다. 검색 요약본은 이 값을 15ppm이라고 잘못 알려줬는데, 그건 30일 이상 장기 기준이었습니다. 원문을 확인하지 않았다면 28배 틀린 값을 쓸 뻔했습니다.
  • 어디까지가 근거이고 어디부터가 가정인지 표시했습니다. NASA 문서에서 나온 값 8개는 이름 앞에 VERIFIED_, 우리가 임의로 정한 값 29개는 ASSUMED_를 붙였습니다. 나중에 누가 표시 없는 값을 몰래 끼워 넣으면 자동 점검이 실패합니다.
  • 사람과 장비를 연결했습니다. 기계만 멀쩡하면 되는 게 아니라, 그걸 다룰 사람이 있어야 시스템이 돌아갑니다. 엔지니어가 갇히면 생명유지장치가 멀쩡해도 못 씁니다.
여기서 중요한 이야기

실제 단위로 계산하고 나니 이전 모델이 현실보다 훨씬 과격했다는 게 드러났습니다. 환기가 돌아가는 상태라면 이 정도 규모의 불로는 일산화탄소가 위험 수준에 도달하지 않습니다. 진짜 위협은 독가스가 아니라 연기 때문에 앞이 안 보여 탈출이 늦어지는 것이었습니다. 계산을 제대로 하지 않았다면 엉뚱한 걸 걱정할 뻔했습니다.

앞으로 해야 할 일

  • 연기 성분 데이터 확보 — 가장 큰 빈칸 "천 1그램이 탈 때 일산화탄소가 몇 밀리그램 나오는가"를 아직 모릅니다. 지금은 추정값입니다. 지상 실험 데이터를 그대로 쓸 수도 없는데, 무중력에서는 불이 타는 방식이 달라지기 때문입니다.
  • 계산기의 작은 결함 수정 특정 조건에서 "귀환 가능" 같은 항목이 실제로는 확인하지 않았는데도 안전하다고 표시될 수 있습니다. 지금은 Phase C가 이 문제를 우회하고 있어 겉으로 드러나지 않지만, 팀원이 새 시나리오를 만들면 바로 문제가 됩니다.
  • 화재 외 사고 유형 감압이나 정전 같은 다른 비상 상황은 아직 없습니다.

B화면

사람이 실제로 손대는 부분입니다. 마우스로 방을 그리고 통로로 잇고, 승무원과 장비를 배치한 뒤, 원하는 방에 불을 지르고 버튼을 누릅니다.

어제 한 일

  • 가짜 계산기를 진짜로 바꿨습니다. Phase B는 원래 그럴듯한 숫자를 지어내는 임시 계산기를 쓰고 있었습니다. 이걸 Phase A 진짜 계산기로 교체했습니다. 화면 코드는 거의 건드리지 않고 어댑터라는 번역기를 하나 끼워 넣는 방식으로요.
  • 고장 난 개발 환경을 고쳤습니다. 받은 파일 안의 가상환경이 다른 사람 컴퓨터 경로를 가리키고 있어서 아무것도 실행되지 않았습니다.
  • AI 분석 탭을 추가했습니다. 결과 화면에 Advisor 탭이 생겼습니다. Phase C의 분석이 여기 표시됩니다.
  • 전달용 압축본을 만들었습니다. 298MB에서 0.3MB로 줄였습니다. 나머지는 받는 사람 컴퓨터에서 자동으로 다시 만들어지는 것들이라 넣을 필요가 없습니다.

앞으로 해야 할 일

  • 오래 걸리는 작업 처리 방식 개선 AI 분석은 30초에서 1분쯤 걸립니다. 지금은 그동안 화면이 기다리기만 하는데, 시간이 더 길어지면 연결이 끊길 수 있습니다. "접수했으니 나중에 확인하세요" 방식으로 바꾸는 게 좋습니다.

C전문가 회의

계산 결과를 놓고 AI 에이전트 7명이 각자 역할을 맡아 회의를 합니다. 사람 조직과 비슷하게 나눠져 있습니다.

  • 화재 담당 — 연기가 어디까지 갔고 어느 통로가 문제였나
  • 승무원 안전 담당 — 누가 얼마나 노출됐고 탈출은 가능했나
  • 시스템 담당 — 어떤 장비가 망가졌고, 고칠 수 있는 고장인가
  • 임무 담당 — 지구로 돌아갈 수 있나, 계속 살 수 있나
  • 근거 담당 — NASA 문서에는 뭐라고 쓰여 있나 결정은 하지 않고 출처만 제시합니다.
  • 반론 담당 — 위 사람들이 뭘 놓쳤나, 누가 과장했나
  • 조율 담당 — 종합해서 권고안 작성 유일하게 "이렇게 하시죠"라고 말할 수 있는 역할입니다.
AI가 거짓말하지 못하게 만든 장치

AI에게 "숫자를 지어내지 마"라고 말로 부탁하는 것만으로는 막히지 않습니다. 그래서 기계적으로 검사하는 장치를 따로 만들었습니다. AI가 답을 내놓으면, 그 문장에 들어 있는 모든 숫자를 계산 결과와 하나씩 대조합니다. 없는 숫자를 말하면 걸러냅니다.

중요한 건 걸러낸 걸 조용히 지우지 않는다는 점입니다. "이 AI가 근거 없는 주장을 하려고 했다"는 사실 자체를 사람에게 보여줍니다. 그게 AI를 얼마나 믿어야 할지 판단하는 재료가 되니까요.

확률처럼 말하지 않는 이유

우리는 여러 가정을 바꿔가며 1000번 계산해 봅니다. 그중 820번에서 승무원이 무사했다면, 우리는 "1000번 중 820번"이라고 씁니다. "82% 확률로 안전"이라고 쓰지 않습니다.

계산을 1000번 반복했다는 사실이 현실 세계의 확률을 증명해 주지는 않기 때문입니다. 우리가 넣은 가정이 틀렸다면 1000번 다 틀린 것이고, 그래도 숫자는 똑같이 820이 나옵니다. "82%"라고 쓰는 순간 없는 근거를 지어내는 셈입니다.

생존·귀환 추정치를 사용하는 방식

이 시스템은 모든 승무원에게 생존 위험이 존재한다고 보고, 산소 부족과 오염물질 노출로부터 가정 기반 생존·귀환 추정치를 계산합니다. 최상위 목적은 제한된 자원에서 기대 귀환 생존자 수를 최대화하는 것입니다. 따라서 어떤 대안은 특정 모듈·장비·승무원을 우선하고, 극단적인 경우 명시적 포기를 포함할 수 있습니다. 이는 임상 예측이나 사람의 가치 평가가 아니라 반사실적 자원 배분 모델입니다.

앞으로 해야 할 일

  • 실제 AI로 한 번도 돌려보지 않았습니다 — 가장 큰 미지수 지금까지의 모든 시험은 "정해진 답을 돌려주는 가짜 AI"로 했습니다. 진짜 Granite에 연결하려면 API 키가 필요합니다. 실제 AI가 우리가 정한 형식을 얼마나 잘 지킬지는 돌려봐야 알 수 있고, 대개 몇 번 다듬어야 합니다.
  • AI 5명의 역할 정의서가 아직 초안입니다 원래 받은 요구사항 문서가 중간에 잘려 있어서, 7명 중 5명의 역할은 제가 추정해서 작성했습니다. 코드에 "초안"이라고 표시해 뒀고, 원본이 나오면 그 부분만 바꾸면 됩니다.

이제 무엇을 하면 되나

순서가 중요합니다. 1번이 나머지 여러 결정의 판단 근거가 되기 때문입니다.

  1. IBM에서 AI 사용 권한 받기
    watsonx 사이트에서 값 세 개를 받습니다 — API 키, 프로젝트 번호, 지역 주소. 그리고 컴퓨터에 그 값을 등록합니다. 등록이 잘 됐는지 확인하는 명령어를 만들어 뒀습니다.

    주의: API 키는 비밀번호와 같습니다. 채팅창이나 메신저에 붙여넣지 마세요.
  2. AI를 한 번 실제로 돌려보기
    화면보다 명령줄에서 먼저 돌려보는 게 좋습니다. 출력이 다 보여서 뭐가 잘못됐는지 찾기 쉽기 때문입니다. 여기서 "AI가 근거 없는 말을 했다"는 표시가 얼마나 나오는지 보고 지시문을 다듬습니다.
  3. AI 5명의 역할 정의서 확정
    원본 요구사항이 있으면 지금 반영하는 게 나중보다 훨씬 쌉니다.
  4. 계산기의 작은 결함 수정
    지금 데모에서는 안 드러나지만, 팀원이 새 우주선을 만들면 바로 나타납니다.
  5. 오래 걸리는 작업 처리 개선
    2번에서 실제로 얼마나 걸리는지 재본 뒤에 결정하는 게 합리적입니다.
시연 관점에서

1번과 2번만 끝내면 처음부터 끝까지 시연이 가능합니다. 우주선 만들기 → 불 지르기 → 계산 → 조치 비교 → AI 분석 → 권고안까지 전부 이어집니다. 나머지는 기능이 없는 게 아니라 더 튼튼하게 만드는 작업입니다.

용어 사전

본문에 점선으로 표시된 단어들입니다. 개발자들이 자주 쓰지만 처음 들으면 막막한 것들만 골랐습니다.

시뮬레이션 simulation
실제로 해보지 않고 컴퓨터로 결과를 미리 계산해 보는 것. 일기예보와 같은 원리입니다 — 내일을 살아보지 않고 계산으로 예측하죠. 계산에 쓰는 프로그램을 시뮬레이터, 그 핵심 계산 부분을 엔진이라고 부릅니다.
명령줄 CLI, Command Line Interface
마우스로 클릭하는 대신 글자로 명령을 입력해 프로그램을 다루는 방식. 검은 창에 명령어를 치는 그것입니다. 반대말은 GUI(버튼과 창이 있는 화면). 문자로 주문하기 vs 메뉴판에서 손가락으로 가리키기의 차이라고 보면 됩니다. 개발자가 명령줄을 쓰는 이유는 빠르고, 무엇이 왜 실패했는지 다 보이기 때문입니다.
터미널 terminal
명령줄을 입력하는 그 검은 창 자체. Windows에서는 PowerShell이나 명령 프롬프트가 여기 해당합니다.
프런트엔드 · 백엔드 frontend · backend
프런트엔드는 사람 눈에 보이는 화면, 백엔드는 뒤에서 계산하고 데이터를 다루는 부분입니다. 식당으로 치면 홀과 주방입니다. 손님은 홀만 보지만 음식은 주방에서 만들어지죠. 우리 시스템에서 Phase B의 화면이 프런트엔드, Phase A 계산기를 돌리는 부분이 백엔드입니다.
API Application Programming Interface
프로그램끼리 대화하는 정해진 창구. 화면이 계산기에게 "이 우주선으로 계산해 줘"라고 요청하는 통로입니다. 식당의 주문서 양식과 비슷합니다 — 양식만 맞춰 적어 내면 주방이 알아서 만들어 주고, 손님이 주방에 직접 들어갈 필요가 없죠.
어댑터 adapter
서로 안 맞는 두 부분 사이에 끼워 넣는 번역기. 해외여행용 콘센트 어댑터와 정확히 같은 개념입니다. 우리 경우 Phase B 화면과 Phase A 계산기가 데이터를 표현하는 방식이 달라서, 그 사이를 번역하는 어댑터를 만들었습니다. 덕분에 화면 코드를 거의 고치지 않고 계산기를 교체할 수 있었습니다.
패키지 · 설치 package · install
남이 만들어 둔 코드 묶음을 가져다 쓰는 것. 매번 처음부터 만들지 않고 이미 검증된 걸 쓰는 게 표준입니다. Python에서는 pip install, 웹 화면 쪽에서는 npm install 명령으로 설치합니다. 요리할 때 밀가루를 직접 빻지 않고 사 오는 것과 같습니다.
가상환경 virtual environment, venv
프로젝트마다 필요한 부품을 따로 담아 두는 상자. A 프로젝트는 옛 버전이, B 프로젝트는 새 버전이 필요할 때 서로 충돌하지 않게 분리합니다. 공구를 프로젝트별 상자에 나눠 담는 것이죠. 주의: 이 상자는 만든 사람 컴퓨터의 경로를 기억하고 있어서, 다른 사람에게 그대로 보내면 작동하지 않습니다. 그래서 압축본에서 뺐습니다.
테스트 test
코드가 제대로 도는지 자동으로 점검하는 프로그램. 사람이 매번 손으로 확인하는 대신, 점검 항목을 코드로 적어 두고 한 번에 돌립니다. 우리 프로젝트에는 225개가 있고, 뭔가를 고쳤을 때 다른 게 망가졌는지 몇 초 만에 알 수 있습니다. 자동차 출고 전 검사 항목표와 비슷합니다.
LLM · 거대 언어 모델 Large Language Model
ChatGPT 같은 글을 이해하고 쓰는 AI. 우리는 이걸 계산에는 쓰지 않고, 계산 결과를 사람 말로 해석하는 데만 씁니다. LLM은 그럴듯한 거짓말을 잘하기 때문에, 숫자 계산을 맡기면 위험합니다.
에이전트 agent
특정 역할과 권한을 부여받은 AI. 같은 LLM이라도 "너는 화재만 본다", "너는 반박만 한다"처럼 역할을 나눠 주면 각자 다르게 행동합니다. 같은 사람이라도 회의에서 맡은 역할에 따라 다른 말을 하는 것과 비슷합니다. 우리는 7개 역할로 나눴습니다.
프롬프트 prompt
AI에게 주는 지시문. "너는 화재 담당이다, 이 규칙을 지켜라, 이 데이터를 보고 답하라" 같은 글입니다. AI의 성능은 프롬프트를 어떻게 쓰느냐에 크게 좌우되고, 대개 실제로 돌려보며 여러 번 다듬어야 합니다.
watsonx IBM watsonx
IBM이 만든 AI 서비스 플랫폼. IBM의 AI 모델을 인터넷으로 불러다 쓸 수 있게 해 주는 곳입니다. 전기를 직접 발전하지 않고 한전에서 끌어다 쓰는 것과 비슷합니다 — 우리가 AI를 직접 만들지 않고 IBM 것을 빌려 씁니다. 이번 공모전이 IBM 주최라서 이걸 씁니다.
Granite IBM Granite
IBM이 만든 LLM의 이름. ChatGPT, Claude 같은 것들과 같은 종류입니다. watsonx가 서비스 플랫폼이라면 Granite는 그 안에서 돌아가는 AI 모델 자체입니다.
API 키 API key
서비스를 쓸 자격이 있음을 증명하는 긴 비밀번호. 이걸 프로그램에 넣어 두면 우리 프로그램이 IBM 서버에 "나 사용 권한 있어"라고 알립니다. 출입 카드와 같아서, 남에게 주면 그 사람이 내 이름으로 쓰고 요금도 나에게 청구됩니다. 채팅창·메신저·문서에 붙여넣지 마세요.
RAG Retrieval-Augmented Generation
AI가 기억에 의존해 답하는 대신, 먼저 실제 문서를 찾아보고 그걸 근거로 답하게 하는 방식. 우리는 NASA 문서 조각들을 저장해 두고, AI가 답할 때 반드시 출처를 함께 대도록 했습니다. 시험을 오픈북으로 치르게 하는 것이죠 — 외운 걸 말하다 틀리는 것보다 책을 펴서 확인하는 편이 정확하니까요.
JSON JavaScript Object Notation
프로그램끼리 데이터를 주고받을 때 쓰는 글로 된 표 형식. 사람도 읽을 수 있게 생겼습니다. 우리 우주선 설계도, 계산 결과, AI의 답변이 전부 이 형식으로 오갑니다.
몬테카를로 Monte Carlo
확실하지 않은 조건들을 조금씩 바꿔가며 여러 번 계산해 보는 방법. 예를 들어 "화재를 30초 만에 발견할 수도, 2분 만에 발견할 수도 있다"면 그 범위에서 무작위로 골라 1000번 계산합니다. 주사위를 여러 번 굴려 보는 것과 비슷해서 도박 도시 이름이 붙었습니다. 결과는 "1000번 중 820번"처럼 횟수로 말하지 확률로 말하지 않습니다.
하드코딩 hardcoding
바뀔 수 있는 값을 코드 안에 못 박아 넣는 것. 보통 나쁜 습관으로 봅니다. 예를 들어 "2번 방을 봉쇄하라"를 코드에 직접 적어 두면 3번 방에 불이 났을 때 못 씁니다. 우리 계산기는 방 번호를 못 박지 않아서 방이 3개든 15개든 돌아갑니다.
